1. Overview

The security model uses defense-in-depth across five layers:

Core principle: No bank credentials or tokens are ever stored. The app does not integrate with financial institutions. All financial data is user-entered or OCR-extracted.

2. Server Security

2.1 Authentication

  • No passwords stored. Email OTP only. No password hashes exist on the server.
  • OTP: 6-digit, valid 5 minutes (expires_in: 300).
  • JWT access token: 15 min TTL. Refresh token: 30 day TTL (rotated).

2.2 Rate limiting

2.3 Household permission enforcement

RoleServer enforcementClient (UI) enforcement
OwnerFull CRUD on all household dataAll buttons visible
MemberCRUD on own + shared; read-only on others'Edit/delete hidden on others' rows
ViewerRead-only on allAdd island hidden, all edit buttons hidden
Server is authoritative. If the UI fails to hide a button, the API rejects the mutation with 403 FORBIDDEN. The UI hiding is a UX optimization, not a security boundary.

2.4 File upload security

  • Max file size: 10 MB. Allowed: image/jpeg, image/png, image/webp, application/pdf.
  • Signed URLs, authenticated access only. No public endpoints.
  • Retention: 90 days (configurable). Files private to uploading user unless household-shared.

2.5 TLS

  • Minimum TLS 1.2. TLS 1.3 preferred.
  • HTTPS only. API base URL via environment variable.

3.2 Token refresh race condition

Request 1 → 401 → acquire refresh lock → POST /auth/refresh → new tokens → release lock → retry Request 2 → 401 → acquire refresh lock (WAIT) → tokens already refreshed → use new token → retry Request 3 → 401 → acquire refresh lock (WAIT) → tokens already refreshed → use new token → retry

Only one refresh HTTP call is made. Waiting callers use the resulting tokens.

4.2 Encryption key management

App launch │ ├─ Read DB encryption key from iOS Keychain / Android Keystore │ ├─ Found? ──▶ use key to decrypt SQLCipher DB │ └─ Not found? ├─ First launch? │ └─ Generate random 256-bit key │ └─ Store in Keychain/Keystore (biometry-protected) │ └─ Create encrypted DB with new key │ └─ Key lost? (uninstall/reinstall, new device) └─ DB is gone — no recovery └─ Server data (if V2 synced) is pulled fresh
  • DB encryption key never leaves the device keychain.
  • iOS: kSecAttrAccessibleWhenUnlockedThisDeviceOnly.
  • Android: AndroidKeyStore provider, TEE-backed.
  • Key is NOT derived from biometrics/passwords — it's a random key generated on first launch.

5.3 Auth provider

enum AuthState { localOnly, authenticated }

class AuthNotifier extends StateNotifier<AuthState> {
  Future<void> login(String accessToken, String refreshToken) async {
    await _secureStorage.write('access_token', accessToken);
    await _secureStorage.write('refresh_token', refreshToken);
    state = AuthState.authenticated;
  }

  Future<void> logout() async {
    await _secureStorage.delete('access_token');
    await _secureStorage.delete('refresh_token');
    state = AuthState.localOnly;  // app still works
  }

  Future<String?> getAccessToken() async {
    final token = await _secureStorage.read('access_token');
    if (token == null) return null;
    if (_isExpired(token)) return await _refresh();
    return token;
  }
}

  • 12 syncable entity rows
  • Household membership graph

  • Sync bookkeeping metadata
  • Notification scheduling data
  • Any passwords (OTP-only, no password hashes)

9. Data Deletion & Account Lifecycle

User taps "Delete account & reset data" │ ▼ Confirmation: "This will permanently delete all your data everywhere." │ ├─ Cancel ──▶ No action │ └─ Confirm: ├─ V2: POST /auth/logout (invalidate tokens) ├─ V2: POST /sync/reset (delete server data) ├─ Local: DROP all tables, recreate empty DB ├─ Clear flutter_secure_storage └─ Restart app → onboarding fresh
  • Household data contributed by deleted user stays for other members.
  • Only personal rows are removed. Creator references are nullified on shared rows.
  • Local-only users (no auth) can reset from Settings — drops local DB, restarts app.

12. V1 Scope Note

  • Auth is disabled. No email OTP, no JWT, no tokens. Auth provider stays in AuthState.localOnly.
  • Sync is inert. Engine built but never runs (no auth → no push/pull).
  • Biometric lock is greyed out. UI exists, toggle disabled.
  • Data stays on device. No data leaves local SQLite DB.

All infrastructure is complete — flipping the switch requires only enabling the auth and biometric toggles. No schema changes or rewrite needed.
